Esta fase entrega la pieza usable a mano por Juan de forma independiente, sin depender de ningún callback todavía inexistente.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client (popover "+ Agregar campo" / "Cargar datos básicos" / edición inline) → Server Action | label/value/category son texto libre del único usuario, pero un cliente modificado podría enviar strings arbitrariamente largos o intentar forzar un `key` propio |
| Server Action → Postgres (`profileFields.key` upsert) | el `key` que llega a la query siempre se deriva server-side vía `normalizeToKey`, nunca viaja del cliente |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | saveProfileFields / updateProfileFieldValue (app/actions/profile.ts) | medium | mitigate | Zod valida label/value/category (longitud, no-vacío) antes de tocar Postgres; el `key` NUNCA se acepta del cliente — se deriva siempre server-side vía normalizeToKey(label), eliminando que un cliente fuerce colisiones o inyecte claves arbitrarias |
| T-05-02 | Tampering | upsertProfileField / updateProfileFieldValue (db/queries/profile.ts) | low | mitigate | Uso exclusivo del query builder tipado de Drizzle (eq, onConflictDoUpdate), nunca SQL crudo interpolado — mismo patrón ya establecido en applications.ts |
| T-05-03 | Information Disclosure | profile_fields (tabla nueva) | low | accept | Mismo modelo de acceso a Postgres que applications/opportunities ya vigente (credenciales de un solo tenant, sin superficie de auth nueva); Juan es el único usuario y esta fase no introduce ningún endpoint público nuevo (el callback gateado por secreto es Phase 6, fuera de este alcance) |

</threat_model>
