# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Scope: PROFILE-01, PROFILE-02, TRACK-05, TRACK-06 — the "Perfil" tab (view/edit flexible key-value profile) and 3 new read-only intermediate application statuses on `StatusDropdown`/`StatusPill`. No new visual language is introduced: this contract extends the locked Impeccable direction shipped in `DESIGN.md` (v1.0) and the `NotesPopover` inline-autosave pattern already in production.

## Layout — Perfil Tab

Fourth `TabsContent` inside `dashboard-tabs.tsx`'s existing `Tabs`, same fixed `100dvh` column frame as the other three tabs (DESIGN.md Layout section) — the tab body owns its own internal scroll, the app frame never scrolls.

**Populated state:** fields render grouped by their free-text `category` column (CONTEXT.md: "contacto", "links", "preguntas comunes", etc.), most-recently-relevant groups first is not required — render groups in the order categories were first created (insertion order), and fields within a group in insertion order. This is **not** a dense `<table>** — profile field count is small (single digits to low dozens), so it uses a simple grouped list, not the Table component reserved for the 3 data-source tabs:

- Each category group is a `card-surface` (`#131316`) container, `rounded-lg` (8px), hairline border (`#232227`), `lg` (16px) internal padding.
- Group header: the category string in **Label** style (13px/500/20px line-height), `muted-ink` color, uppercase not required (keep as typed).
- Fields within a group: one row per field, `sm` (8px) vertical padding, a hairline-border divider between rows (never the last row), matching the Table component's "hairline dividers only, no zebra striping" rule.
- Each row: `label` (the human-readable field label, Body style, `warm-off-white`) left-aligned, `value` (Body style, `warm-off-white`) right-aligned or in a second column, and a trailing edit-trigger icon button (see Interaction Pattern below). Long values (e.g. a full CV/resume URL) wrap normally — **no line-clamp/truncation**: DESIGN.md's line-clamp rule exists specifically for the dense multi-thousand-row Table density model and does not apply to a short, low-row-count settings-style list.
- Category groups stack with `xl` (24px) gap between them (DESIGN.md declares tokens only up to `lg`/16px; this phase extends the scale with `xl`=24px and `2xl`=32px for section-level spacing not previously needed — both remain multiples of 4, consistent with the project's existing Tailwind utility usage).
- Below the last group (or standalone if the profile has ≥1 field): a persistent "+ Agregar campo" `Button variant="outline"` — always visible once at least one field exists, left-aligned under the groups, `2xl` (32px) top margin separating it from the last group.

**Empty state (zero fields):** matches the existing minimal empty-state convention already shipped in `virtualized-opportunities-table.tsx` (`py-10 text-center text-muted-foreground`, plain text, no icon-tile, no card — DESIGN.md's "no hero-metric template, no decorative icon tiles" Don't) — extended with a CTA, since unlike the filtered-table empty state this one has an action:
- Heading line (Body weight raised to Label's 500, `warm-off-white`): "Tu perfil está vacío"
- Body line (`muted-ink`, Body size): "Carga tus datos básicos para que las postulaciones asistidas por IA puedan usarlos, o agrega un campo a mano."
- Primary CTA button (`Button variant="default"`, which resolves to the theme's `radix-nova` primary — the project's one sanctioned primary-action use of Signal Violet, DESIGN.md One Accent Rule role #3): "Cargar datos básicos"
- Secondary link/button directly below or beside it, same visual weight as the persistent one in the populated state: "+ Agregar campo" (`Button variant="outline"`) — so Juan is never forced through the 6-field bulk form if he only wants to add one ad hoc field.

## Interaction Pattern — Inline Field Edit (matches `NotesPopover`)

Both "edit an existing field's value" and "+ Agregar campo" / "Cargar datos básicos" reuse `NotesPopover`'s exact autosave shape — same `useState` + debounced `useTransition` + Zod-validated Server Action structure, same trigger→Popover→text-indicator UX, no new interaction vocabulary:

**Edit existing field (per-row):**
- Trigger: the row's trailing icon button (`variant="ghost" size="icon" className="size-8"`, `aria-label="Editar {label}"`), a `Pencil` (lucide) icon — parallel to `NotesPopover`'s `StickyNote` trigger, but `Pencil` since there is no "has content vs. empty" fill-vs-outline distinction needed here (a profile field always has a value once it exists).
- `PopoverContent` (`align="start"`, `className="w-80"`): a `<label htmlFor>` showing the field's `label` (not `key`) in the same `text-xs font-medium text-muted-foreground` style as `NotesPopover`, then an `Input` (not `Textarea` — profile values are single-line) bound to local state.
- Autosave: identical 500ms debounce constant (`DEBOUNCE_MS = 500`), identical `SaveState` union (`"idle" | "saving" | "saved"`), identical `aria-live="polite"` text row below the input: "Guardando…" while pending, "Guardado" once resolved, a single non-breaking space while idle. No visible error banner — on a rejected Zod validation or write failure, revert `saveState` to `"idle"` and `console.error` (matching `NotesPopover`'s and `StatusDropdown`'s established "no toast/error-banner system yet" convention for this single-user tool; not a regression, a deliberate parity choice per CONTEXT.md's "mismo patrón que NotesPopover" instruction).
- `Escape`-to-close + focus-return-to-trigger: native Radix Popover behavior, no custom override (same as `NotesPopover`).

**"+ Agregar campo" (new field, ad hoc):**
- Trigger: `Button variant="outline"` labeled "+ Agregar campo" (persistent below the groups, or the empty-state secondary action).
- `PopoverContent` (`className="w-80"`): three stacked `<label>`+`Input` pairs — Categoría (native `<input list="…">` `<datalist>` populated from the profile's existing distinct `category` values, so Juan can reuse "contacto"/"links" without retyping, but can also free-type a new category — no shadcn Combobox needed), Etiqueta (the human-readable `label`), Valor. A single "Guardar" `Button` (not autosave-per-keystroke here, since three interdependent fields must land together as one row) submits all three; same `saveState` text-row convention below the button ("Guardando…"/"Guardado"), popover stays open after save so Juan can add another field immediately, input values clear after a successful save.
- `key` is derived server-side from `label` (snake_case normalization, per CONTEXT.md "`key` normalizada... + `label` legible aparte") — never a field Juan types directly, avoiding invalid/duplicate keys entirely.

**"Cargar datos básicos" (empty-state bulk CTA):**
- Trigger: the empty-state primary CTA button.
- `PopoverContent` (`className="w-96"`, wider than the single-field popovers to hold 6 rows without feeling cramped): 6 `<label>`+`Input` pairs pre-seeded with `category="contacto"` for nombre/email/teléfono and `category="links"` for CV/LinkedIn/GitHub (CONTEXT.md PROFILE-02 field list) — labels: "Nombre completo", "Email", "Teléfono", "Link CV/resume", "LinkedIn", "GitHub". Any subset may be left blank; only non-empty fields are created as rows. Single "Guardar" button, same saving/saved text-row convention, closes the popover on success (unlike the ad hoc add-field popover, since this is a one-time bulk action, not a repeat-and-add flow).

## Status Extension — Intermediate Auto-Apply States

Extends `STATUS_META`/`APPLICATION_STATUSES` (currently 6 values, no per-status color, icon+label only) with 3 new **read-only** values: `auto_fill_in_progress`, `ready_to_review`, `submitted`.

**Selectability contract (functional, load-bearing for the visual spec):** the 3 new values are valid `status` column values and a valid current `StatusDropdown` display state, but they must **never appear as a `SelectItem` inside `SelectContent`** — only the existing 6 manual statuses remain pickable. `StatusDropdown`'s `SelectValue` already renders custom children (`<CurrentIcon/>{label}`) decoupled from the options list, so displaying a non-listed current value requires no structural change. The trigger itself stays enabled even when the current status is one of the 3 — Juan can always manually override an auto status back to a manual one (e.g. mark `rejected` after reviewing a stalled auto-fill session); he simply can never select *into* an auto status by hand.

**Visual distinction — resolving a tension with DESIGN.md's One Accent Rule:** CONTEXT.md asks these 3 to "reuse the violet Impeccable palette" while DESIGN.md's Named Rule restricts Signal Violet (`#7c6cf6`) itself to exactly 3 roles (active tab, focus ring, primary/active interactive state) — "a fourth use is a bug, not a style choice." The resolution used here does **not** add a 4th use of raw Signal Violet: it reuses **Violet-Tint Surface** (`#1e1930`), the same secondary-tier token DESIGN.md already sanctions for the existing "Open" `StatusPill` and active filter chips. This keeps the new states legibly "on-brand violet" without touching the One Accent Rule's actual constraint (which governs the accent color itself, not its low-saturation tint).

| Status | Icon (lucide) | Trigger background | Trigger text | Label (Spanish) |
|--------|--------------|---------------------|---------------|------------------|
| `auto_fill_in_progress` | `Hourglass` | `violet-tint-surface` (`#1e1930`) | `warm-off-white` (`#e7e5e1`) | "Auto-fill en curso" |
| `ready_to_review` | `Eye` | `violet-tint-surface` (`#1e1930`) | `warm-off-white` (`#e7e5e1`) | "Listo para revisar" |
| `submitted` | `CircleCheck` | `violet-tint-surface` (`#1e1930`) | `warm-off-white` (`#e7e5e1`) | "Enviado (auto-apply)" |

Icon collision check against the 6 existing statuses (`Bookmark`/`CircleDashed`/`Send`/`Clock`/`XCircle`/`CheckCircle2`): none of `Hourglass`, `Eye`, `CircleCheck` are reused — `Hourglass` reads as "time passing" without colliding with `in_progress`'s `Clock`; `CircleCheck` (thin stroke, outline check-in-circle) is a visually distinct lucide export from `accepted`'s `CheckCircle2` (bolder two-tone check), satisfying CONTEXT.md's explicit "check outline, distinct from the existing filled check" requirement. `submitted`'s label is deliberately spelled out as "Enviado (auto-apply)" rather than a bare "Enviado" so it never reads as a synonym of `applied`'s "Aplicado" at a glance — text must disambiguate, not just icon/color, per DESIGN.md's Never-Color-Alone Rule extended to "never same-looking-copy alone" for two semantically different completion states.

The 6 manual statuses' `SelectTrigger` keep their current plain/neutral background (no tint) — only a current value that is one of the 3 auto states gets the `violet-tint-surface` fill. This is the entire visual signal: "if the control looks tinted, Juan didn't set it by hand."

`StatusPill` (`status-pill.tsx`, the open/closed opportunity indicator) is untouched by this phase — it has no relationship to `ApplicationStatus`; only `StatusDropdown`'s `STATUS_META` record is extended.

## Spacing Scale

DESIGN.md (locked v1.0) declares 4 tokens up to `lg`; this phase extends the scale for the Perfil tab's section-level grouping, which the existing 3 data-source tabs never needed. All values remain multiples of 4 except the two inherited from DESIGN.md itself (`xs`/`sm` are DESIGN.md's own pre-existing 6px/8px, carried forward verbatim rather than rounded, to avoid a mismatch with already-shipped screens):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 6px (`0.375rem`, DESIGN.md) | Icon gaps, inline padding — inherited, unchanged |
| sm | 8px (`0.5rem`, DESIGN.md) | Compact element spacing, field-row vertical padding |
| md | 12px (`0.75rem`, DESIGN.md) | Default element spacing |
| lg | 16px (`1rem`, DESIGN.md) | Category-group internal padding |
| xl | 24px | New for Phase 5 — margin between the last category group and the "+ Agregar campo" button |
| 2xl | 32px | New for Phase 5 — vertical gap between stacked category groups |

Exceptions: none.

## Typography

DESIGN.md's locked type scale (5 declared steps, 3 weights: 400/500/600) is carried forward verbatim — Phase 5 does not introduce a 4th weight or a 6th size. Deviating from DESIGN.md's already-shipped scale here would visibly mismatch the 3 existing tabs.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 15px (`0.9375rem`) | 400 | 24px (`1.5rem`), tracking `-0.01em` — field labels/values, empty-state body copy |
| Label | 13px (`0.8125rem`) | 500 | 20px (`1.25rem`) — category group headers, popover form `<label>`s, "+ Agregar campo"/CTA button text |
| Heading | 17px (`1.0625rem`) | 600 | 24px (`1.5rem`) — reserved, not used within the Perfil tab body itself (the tab switcher already labels the section; no in-tab page title is added) |
| Display (data-mono) | 11px (`0.6875rem`) | 400 | 16px (`1rem`), `tabular-nums` | Reserved for any future numeric/timestamp display (e.g. "última actualización") — not used by any field in this phase's shipped scope |
