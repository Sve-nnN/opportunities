<objective>
Construir el endpoint de callback de auto-apply: una ruta API gateada por bearer secret (`AUTO_APPLY_CALLBACK_SECRET`) que una sesión externa de Claude Code invoca al terminar (o pausar a medias) una sesión de auto-fill, y que actualiza `applications.status`/`notes`, hace upsert de los campos de perfil que esa sesión aprendió, y deja un registro de auditoría — todo en una sola transacción atómica, validada del lado del servidor sin confiar ciegamente en el caller.

Purpose: CALLBACK-01/02, PROFILE-03 y AUDIT-01/02 son la mitad "escritura" de v1.1 — Phase 7 (Send to AI, fuera de este alcance) generará el prompt que arranca una sesión externa, pero esa sesión necesita este endpoint ya construido y probado para poder reportar su resultado de vuelta. research/PITFALLS.md Pitfall 2 es explícito: el caller no es Juan escribiendo un curl a mano, es la interpretación de un LLM de una página web arbitraria — por eso la validación server-side (transición de estados solo-avanza, colisión de perfil aborta la escritura completa, tope de tamaño en los arrays) no es una mejora futura, va en esta misma fase, no después de un incidente.
Output: tabla `application_history` + migración, `AUTO_APPLY_CALLBACK_STATUSES`/`isForwardAutoApplyTransition` en `application-status.ts`, `opportunityExistsByExternalId` en `queries/opportunities.ts`, `upsertProfileField` extendido para correr dentro de una transacción, `queries/application-history.ts`, la ruta `POST /api/applications/[externalId]/apply-session`, y `scripts/verify-apply-session.ts` cubriendo el contrato completo contra Postgres real + HTTP real.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Sesión externa de Claude Code (semánticamente no confiable) → apply-session route | El caller tiene el bearer secret, pero el payload que envía es la interpretación de un LLM de una página web arbitraria (research/PITFALLS.md Pitfall 2) — el secret prueba "es una sesión que Juan inició", no que el contenido del payload sea correcto |
| apply-session route → Postgres (applications / profileFields / applicationHistory) | Toda escritura pasa por una sola db.transaction() — nunca hay una ventana donde dos de las tres tablas queden desincronizadas entre sí |
